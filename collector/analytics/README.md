**Rollback on Grafana 13.1.1:** Org DELETE may fail with an opaque HTTP 500 (`Failed to delete organization`); the server log must independently show the same request and the precise `failed to delete dashboards for org <id>: the server does not allow this method on the requested resource` error. Supply a locally readable server log with `--grafana-error-log`; without fresh matching evidence, an HTTP 500 fails closed. Rollback first removes receipt-owned dashboards, datasource and folder, verifies the org has no dashboards/folders/datasources and only the approved Admin, revokes owned role LOGIN and database CONNECT, then attempts org deletion. For that specific failure only, it records `retained_org` (ID, name, admin, reason) in the private fsynced receipt, finishes empty rehearsal-database and role deletion, rechecks the empty org, and exits nonzero with `rollback incomplete`. Repeat rollback is safe and still reports incomplete; subsequent apply may reuse **only** that receipt-owned, unchanged, empty admin-only org. Unknown errors or ownership/content drift fail closed; do not adopt an existing foreign org. The retained org is residual metadata, **not zero-resource cleanup**, and must be tracked for future Grafana repair/removal. Main Org and fleet dashboards are not touched. A database containing telemetry is *not* dropped: keep its login disabled and require an explicit archive/retention decision before any destruction. An interrupted rollback or disabled credential is not silently accepted as active apply. This is a source policy, not approval to activate production.

**Boundaries:** tool_count batches and tool_metrics summaries must not be added as independent calls.
The health panel reports Unknown without a checkpoint or valid receipt in the selected receipt window, Stale after a bounded two-hour receipt gap within that window, and Partial on invalid event timestamps among receipts in the selected window. Receipt evidence is bounded inclusively from the selected start through the selected end; future receipts cannot establish freshness. Missing/invalid receipt timestamps cannot be assigned to any receipt window, so they do not cause perpetual Partial or count as recent receipts; the separate all-history timestamp-quality table retains their visibility. A recent receipt is not proof that the upstream collector is delivering every event. Importer failures after the last successful checkpoint are measurable only through the external scheduler exit-code alert; a failed transaction leaves the last checkpoint untouched, and freshness becomes Stale while the last receipt remains inside the selected window, then Unknown when it falls outside. A source with no new lines can have a fresh importer checkpoint but no fresh receipt and must not be labelled healthy. Historical records with missing/invalid event or receipt timestamps are preserved with explicit quality categories and excluded from event-time windows or receipt lag as appropriate; the all-history quality table counts them without exposing raw payload. Invalid metric axes or inconsistent totals abort the entire transaction without checkpoint advance. Axis distributions are separate marginals (outcomes, durations, features), never summed together or with schema-1 count batches. Provision schema changes in a new disposable/approved database; issue 63 now supplies migrate_issue63.sql specifically for the baseline analytics schema; other earlier schemas still require independent reconciliation. Legacy no-ID records use source offset identities, so a source copied to another path requires manual reconciliation. The imported `raw` column contains only schemaVersion (not raw payload). The SQL roles are a deployment template and tests require a disposable database. Source tests do not prove Grafana visual rendering, role grants on production, protocol ACK, or live receipt lag.
